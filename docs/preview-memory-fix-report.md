# 画像プレビューのメモリ抑制(iPhone の再読み込みループ対策) — 実装報告 2026-09-23

## 事象
ファイル(PCEXPORT)を読み込んで画像を登録しながらしばらく使うと、iPhone でページの再読み込みが繰り返される。

## 原因(調査で確定した範囲)
- `index.html` に再読み込みを起こす処理は無い(`location.reload` / meta refresh / Service Worker なし)。公開ページと手元は同一バイト。デスクトップ実ブラウザでは貼り付け→解析→再読み込みを繰り返しても再遷移・例外ゼロ。
- したがって WebKit のメモリ上限超過によるページ強制終了と Safari の自動再読み込みの反復と判断。該当箇所:
  1. 追加した写真を原寸のまま `URL.createObjectURL` で `<img>` に表示していた(1枚のデコードで数十MB、最大5枚)。
  2. 画像レビュー側の object URL(`reviewBlobUrls`)は項目を移動しても解放されず、使うほど蓄積していた。
  3. 保存時は `Promise.all` で全画像を同時に `arrayBuffer()` へ展開して SHA-256 を計算していた。

## 変更
- `window.PersonaPreview`(共通の縮小器): 長辺 1280px を超える画像は JPEG(0.82)に縮小してから object URL を作る。縮小できない形式は原寸で表示(従来どおり)。器はビュー毎に独立(`create()`)。
- 画像レビュー: `loadImagePreview` が縮小 URL を使う。`renderReviewItem` で表示中の項目の画像以外を解放。削除・解析・クリア時も同じ器で解放。保存は `persistOneImage` を 1 枚ずつ逐次実行。
- A/B: `setPreview` / `hydratePreviews` が同じ縮小器を使い、`hydratePreviews` は逐次読み込み。出来上がり次第 `render()` で反映。ケース移動時の解放(`releaseAllPreviews`)は従来どおり。
- 保存する実体(IndexedDB)は原寸のまま。SHA-256 も原寸に対して計算する(記録の互換性は不変)。

## 検査
`scripts/check_preview_memory.cjs`(実ブラウザ・合成画像のみ): 縮小 URL(長辺 ≤1280、原寸 blob から URL を作らない) / 項目移動での解放と復帰 / 保存の逐次実行(同時読込ピーク=1) / 再読み込み後の再生成と実体が原寸のまま / 縮小器の単体。`run_ab_review_release_gate.cjs` に追加。

## 残る確認(利用者側)
公開反映後、iPhone で画像を登録しながら 20〜30 件ほど進めて再読み込みが起きないことを確認する。
起きる場合は Safari の「Webサイトデータ」の当該サイト容量と、発生直前の操作(登録直後か、移動中か)を控える。

## 追補 2026-09-24: 再読み込みされても作業を失わない

### 事象(公開後も継続)
iPhone で「問題が起きたため、このウェブページが再読み込みされました」の後、真っ白な読み込み中になる。

### 原因の見直し
起動処理は画像を1枚も読まない(A/B は画面を開いたときだけ初期化、レビューは本文のみ描画)。起動時に落ちているのではなく、
画像生成アプリ等へ切り替えている間に iOS が Safari のページを破棄し、戻ったときに Safari が最初から読み直している。
読み直すと「抽出」画面に戻り、レビュー画面で付けたまま保存していない画像・評価・メモ(メモリ上だけにあった)は失われていた。

### 変更
- 開いていた画面(抽出/レビュー/A/B)を記録し、読み直したら自動でその画面へ戻す。
- レビューの画像は付けた時点で画像DBへ仮置きし、未保存の下書き(画像の順・評価・メモ・比較メモ)を入力のたびに端末へ書き留める。
  読み直した後はそのまま続けて保存できる(保存時は仮置きした原寸から SHA-256 を計算。記録の形式は従来どおり)。
- 別アプリへ切り替えたら表示用の画像を解放し(破棄されにくくする)、戻ったら表示中の分だけ読み直す。
- A/B の入力は従来から入力の時点で書き留めているため、そのまま。

### 検査
`check_preview_memory.cjs` にフェーズ5を追加: 未保存の画像2枚とメモが読み直し後に戻る / タブを押さずにレビュー画面へ戻る /
そのまま保存でき原寸の SHA-256 が付く / 非表示で画像を解放し、表示で戻る。リリースゲート 13/13 PASS。

## 追補2 2026-09-24: 開く途中で落ちる → 再読み込みの連続(「問題が繰り返し起きました」)

### 症状(利用者の説明)
ページを開くと再読み込みが連続で点滅し、やがて止まって「"…/persona_generator/"で問題が繰り返し起きました」と出る。
= 起動の途中で必ず落ちている。

### 原因(コードで確認した範囲)
A/B の案内付きモードは開くたびに `guidedScanBlobs` で**登録済みの全画像の実体を同時に**読み出して有無を確かめていた。
画像が増えるほど開いた瞬間のメモリが跳ね上がる(「最近になって」と一致)。追補1の「前の画面へ自動で戻す」で
A/B が起動のたびに開くようになり、毎回ここで落ちる形に悪化した。

### 変更
- `guidedScanBlobs`: 実体を読まず、1回の接続で `count(key)` だけを確かめる。
- 起動ガード: 起動が安定(20秒)に届かずに終わったら、次の起動は安全モード(自動復帰と画像表示を止める)。記録には触れない。
  「通常モードで開き直す」で戻せる(`?safe=0`)。`?safe=1` で明示的に安全モード。
- 起動の各段階を端末に記録し、安全モードの画面に「落ちる直前の記録」として表示・コピーできる。
- 見出しに版(`版 2026-09-24d`)を表示し、更新の反映を一目で確認できる。

### 検査
リリースゲート 13/13 PASS。実ブラウザで Page.crash による実クラッシュ後に安全モード・自動復帰の停止・直前記録の表示・通常モードへの復帰を確認。

## 追補3 2026-09-24: 実測で特定した不具合(抽出画面の使い方)

### 再現方法
利用者の手順(ファイル読込→解析→本文コピー→別アプリへ切替→ページ破棄→読み直し を繰り返す)を
Playwright WebKit(iPhone 13 相当)で再現し、WebContent プロセスのメモリ(RSS)と保存の成否を測った。
入力は app_static の CLI で作った実物のエクスポート(50件=787KB、200件=3.1MB)。

### 実測値(修正前)
| 段階 | 50件 | 200件 |
|---|---|---|
| 起動直後 | 120MB | 120MB |
| ファイルを入力欄に表示 | +45MB | +143MB |
| 解析・保存 | +20MB | +59MB、**localStorage への保存が容量超過で無言の失敗** |
| 読み直し後の復元 | 50件 | **0件(全件消失)** |

### 原因
- 読み込んだファイルの全文を画面上の入力欄に表示していた(ファイルの約45倍のメモリ)。
- 全件(本文+設定オブジェクト+設定の元文字列)を localStorage に書いていた。sgktmr808.github.io の6アプリ共有の約5MB枠を
  超えると無言で失敗する。前後移動のたびに全件を書き直していた。
- 生成設定が 8/24〜25 から1件約1.9KB→約8.4KBへ増え(app_static の生成設定記録で確認)、同じ件数でもエクスポートが約4.5倍になった。
  persona_generator のコードが変わらなくても「最近になって」起き始めた理由。

### 変更
- ファイルは入力欄に表示せず、読み込んだらそのまま解析する(貼り付けは従来どおり)。
- 解析した全件は IndexedDB に1回だけ保存し、localStorage は位置情報だけ。保存に失敗したら画面に表示する。
- 旧形式(全件が localStorage)は起動時に IndexedDB へ移す(データを失わない)。

### 実測値(修正後)
| | 50件 | 200件 |
|---|---|---|
| 読込・解析時のピーク | 185MB→148MB | 322MB→184MB |
| 読み直し後の復元 | 50件 | 0件→200件 |

リリースゲート 13/13 PASS。旧形式からの移行(30件→IndexedDB→移動→読み直しで6件目を表示)を WebKit で確認。

### 未確定の点
iPhone 実機の「開く途中で落ちる」の直接の記録(iOS の JetsamEvent / WebContent のクラッシュログ)はまだ取れていない。
上の修正で抽出画面のメモリの山と保存の失敗は消えたが、実機の症状が止まったことは利用者の確認待ち。
