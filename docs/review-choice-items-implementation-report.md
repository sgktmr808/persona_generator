# 追加レビュー項目とスロット交互キュー — 実装報告

対象: 公開レビューUI（`index.html`）の**汎用機能**2件。
特定の実験の本文・ID・画像・評価値・判定閾値は、この報告にもコードにも入れない。
実験の中身は利用者が手渡すパッケージファイルの中だけに存在する。

---

## 1. `policy.reviewChoiceItems` — パッケージが宣言する追加レビュー項目

### 何を解いたか

既存のレビュー欄は、判定・スコア・失敗分類・コメントに加えて、実験ごとに1項目だけを足せる作りが
2つ（`focusRubricRequired` の3段階入力と `opticalIntentAlignmentRequired` の単一選択）あった。
どちらも**そのキー名がUI側に焼き込まれている**ため、別の観点を1つ足すたびにUIへ実験固有の語が増える。

`reviewChoiceItems` は、**1問1答の単一選択を必要な数だけ**パッケージが宣言できる汎用の器である。
UIは設問文も選択肢も選択肢の意味も1つも決めない。

### 宣言の形

```json
"policy": {
  "reviewChoiceItems": [
    {
      "key": "someItemKey",
      "label": "画面の見出し（省略時は question）",
      "question": "設問文",
      "required": true,
      "note": "補足（任意）",
      "options": [
        { "value": "a", "label": "短文", "description": "その選択肢の意味（その場に表示する）" },
        { "value": "b", "label": "短文", "description": "…" }
      ]
    }
  ]
}
```

### 読み込み時の検証（fail closed）

壊れた宣言は黙って捨てず、**読み込み自体を拒否する**。捨てると「全項目に答えた」が項目の欠けたまま
成立してしまう。拒否のとき既存の記録には触れない。

- 配列で1件以上
- `key` は `^[A-Za-z][A-Za-z0-9_]{0,63}$`
- `key` が既存の評価項目名（`verdict` / `failures` / `notes` / `priorityChecks` /
  `focusAssessment` / `opticalIntentAlignment` / `reviewChoices` ほか）や `scoreKeys` と衝突しない
- `key` が重複しない
- `question` が空でない文字列。`label` / `note` は与えるなら空でない文字列
- `required` は真偽値
- `options` は2つ以上、`value` が空でなく重複せず、`label` が空でない、`description` は与えるなら空でない

### 画面

- 判定 → 合焦（宣言時） → スコア → 狙いとの一致（宣言時） → **追加項目** → 重要要素（宣言時） →
  失敗分類 → コメント の順に出る。宣言の無いパッケージでは入れ物ごと隠れる。
- 選択肢はラジオの縦積み。**各選択肢の意味を短文の下にその場で出す**ので、専門語だけを見せて
  解釈を任せない。行は `min-height: 44px`、説明は折返し可。
- 保存値は宣言された `value` だけ。宣言外の値は復元時に空へ落ちる。

### 保存と書き出し

- 端末の記録: 値があるときだけ `review.reviewChoices = { key: value }` を足す。
  宣言の無いパッケージの記録には**キーを1つも足さない**（既存の評価ハッシュを変えないため）。
- 書き出し: `images[].evaluation[key] = value`。値のあるものだけを出す。
- 完了・書き出しの門: `required: true` の項目が1つでも空なら、保存も書き出しも通らない。
  画面下部の「未入力 N 件」に項目名で残数が出る。`required: false` は完了を止めない。

## 2. `experiment.generationExecution.slotSequencing` — 面の並べ方

案内付き実行キューは、これまで「片面の1..N枚をすべて撮ってから、もう片面の1..N枚」に固定だった。
枚数が増えると同じ面が長く連続し、作業中に画像サービス側が変化した場合その影響が片方の面へ偏る。

パッケージが並べ方を宣言できるようにした。

| 値 | 並び（必要枚数2の例） |
|---|---|
| `grouped-by-slot`（宣言が無いときの既定） | B1 B2 A1 A2 |
| `alternating-slots` | B1 A1 B2 A2 |

- 宣言が無ければ従来どおり。**既存パッケージのキューは1件も変わらない。**
- UIは宣言された `items` を証拠にせず、`cases[].generationOrder` と `cases[].slotRoles` と
  この並べ方から**期待キューを再導出**して突き合わせる。1項目でも食い違えば案内付きの作業台を出さない。
- 対応外の値（例: `random-slots`）は読み込みを拒否する。
- キューに役割語（control / treatment）は出ない。画面に出るのは ケースID・面・何枚目 だけ。

## 3. 受入検査

`scripts/check_ab_review_choice_items.cjs`（合成フィクスチャのみ・実ブラウザ）。
`scripts/run_ab_review_release_gate.cjs` の逐次リリースゲートへ追加した。

確かめていること:

1. 宣言の無いパッケージでは項目も保存キーも1つも増えない
2. 壊れた宣言 16 種を1つずつ拒否し、拒否のたびに保存内容がバイト不変
3. 交互キューが12手順・A/B交互・各面6枚で提示され、同じ面が連続しない
4. まとめ撮りの宣言は従来どおりの並びのまま
5. 押した「この本文をコピー」自身に 成功 → 失敗（再試行） → 復帰 が出る
6. 各選択肢の意味がその場に表示され、選択肢の行が44px以上
7. 画像切替の往復・再読み込みで全評価値と全画像が復元する
8. 必須項目が空なら保存も書き出しも止まり、残数が画面へ出る。任意項目は止めない
9. 書き出し・再取込で12画像・SHA-256・全評価値が一致する
10. 1280 / 320 / 375 / 390 / 430 / 844×390 で横溢れ0・操作44px以上・入力16px以上
11. 検査の書き出しが利用者の Downloads へ1件も出ない（使い捨ての保存先へ固定し、前後差分を検査）
