## 1. 何を変えたか

R3-FB は保存・復元・書き出しの受入検査には通っていたが、内部の記録手順をそのまま画面へ並べていたため、
**16ケースを反復して画像を見比べる作業台としては成立していなかった**。
R3-FC はデータ契約を一切変えずに、画面の主語を利用者の作業順へ組み替えた。

| | R3-FB | R3-FC |
|---|---|---|
| 生成条件 | ケースごとに provider/model/Seed を入力しないと画像を登録できない | **一度だけ**登録し、以降のケースへ自動で引き継ぐ。ケースごとの `condition` 行は必要時に内部生成 |
| 本文 | 3,000字級の本文が常時2枚分表示され画面を占有 | 既定で折りたたみ。「本文をコピー」が主操作 |
| 画像登録 | ファイル選択 →「A/B に画像を登録」ボタンの2操作 | **選択・ドラッグ&ドロップのどちらでも選んだ瞬間に登録**。登録ボタンは廃止 |
| 比較表示 | ページ下部の別カードへ隔離 | A/B の作業列の中で大きく横並び(狭い画面は縦並び) |
| 評価 | 画面下の共有フォームで1枚ずつ対象を選び直す | **各画像の直下にインライン**。A と B を同時に入力できる |
| 保存 | 評価保存 →(別操作で)比較保存 | **「この比較を保存して次へ」1操作**でレビュー2件+比較1件を保存し、次の未完了ケースへ |
| 現在地 | 進捗テキストのみ | 固定ヘッダーに実験名・`ケース n / 16`・完了件数・状態(`未生成 / Aのみ / Bのみ / 評価待ち / 完了`)・前/次/未完了へ |

内部識別子(conditionId / reviewId / comparisonId / supersedes / ハッシュ / IndexedDB)は主導線に出していない。

## 3. 操作フロー

1. **A/B実験**タブ →「パッケージを読み込む」。schemaVersion / 各armの本文SHA-256 / integrity /
   definitionSha256 を照合し、1つでも合わなければ読み込まない。
2. **「どこで画像を作りますか？」**。`ChatGPTで生成` を押せばそれだけで始まる。
   `その他` を選んだときだけ provider / model / Seed の欄が開く。この画面は最初の1回だけ出る。
3. 作業台へ。固定ヘッダーで現在地と状態が分かる。
4. 「本文をコピー」で A を取り出して生成 → 画像を A 列へ**ドロップまたは選択**。置いた瞬間に登録され、
   そのまま大きく表示され、比較対象になる。B も同様。
5. 各画像の直下で判定・美的満足度・意図一致・失敗分類・コメントを入力。
6. 「どちらが良いか」と比較コメントを入れ、**「この比較を保存して次へ」**。
   レビュー2件と比較1件を保存し、次の未完了ケースへ自動で移る。
7. 片側しか画像が無いときはボタンが「A の評価だけ保存する」に変わり、個別レビューだけを保存する。
   このとき比較行は作らず、順位1位・採用扱いにもしない。
8. 誤って置いた画像は、その画像のすぐ下の「この画像を外す」で外す(確認あり)。記録は残り、
   書き出しからは外れる。外した画像を比較に使っていた場合、その対象は未完了へ戻る。
9. 書き出しは最下部の「書き出しと管理」に格納。完了件数と未完了ケース番号を先に表示する。
   「生成条件を変更」で provider / model / Seed を後から変えられる。

## 4. 保存互換性

**保存形式は R3-FB のまま**。localStorage キー `personaGenerator.abExperiment.v1`、
IndexedDB `personaGeneratorAbImages` / `abImagesV1`、各行の形(`conditions` / `images` / `reviews` /
`comparisons` / `invalidations`、append-only + `supersedes`)、JSONL 3種の形式をいずれも変えていない。

追加したのは後方互換の任意項目 `defaultCondition`(全ケースへ引き継ぐ生成元)だけ。
これを持たない R3-FB の記録を読んだときは、既存の `condition` 行から推定して1度だけ書き戻す。
**移行処理は行わない。**

`check_ab_r3fb_record_compatibility.cjs` が、R3-FB 形式の記録(`defaultCondition` 無し・
`conditions`/`images`/`reviews` あり)を置いた状態で開き、作業台が出る・生成元の再入力を求めない・
既存画像/レビュー/条件が保持される・本文が変わらない・既存レビューが全項目載り直す、を確認している(11件 PASS)。

`adoptionDecision: "not-applicable"` と「順位・preference は採用判定として扱いません」の表示も維持している。

### 回帰フェーズが確認する6観点(指摘4)

1. 本文を改ざんしたパッケージを拒否し、読込済みのパッケージ・本文・記録を置換しない。
2. 同一定義(日時だけ違う)の再読込では、記録・画像実体3件・生成元をすべて保持し、確認も求めない。
3. 定義変更を**拒否**すると、記録・画像実体・生成元・画面のいずれも変わらない。
4. 定義変更を**承認**すると、旧記録・画像実体(3→0)・`defaultCondition` を消してから新定義を載せ、
   生成元の選択画面へ戻る(入力欄にも前の値が残らない)。
5. 画像を外すと比較が stale になり、完了件数から外れ、比較JSONLは0行、レビューJSONLからも
   その画像が消えて `bestImageId` が空になる。行自体は残る(物理削除しない)。
6. 「この実験の記録を削除」で全記録・画像実体・生成元が消え、パッケージだけ残して生成元登録へ戻る。

### 実装中に見つけて直した欠陥(2件)

- **入力中の評価が消える**: 重複画像など「1枚も増えなかった」登録でも `prefillReview()` を
  無条件に呼んでいたため、書きかけの判定・コメントが消えた。追加が実際にあったときだけ載せ直すよう修正。
- **片側だけのケースを永久に保存できない**: 必須判定に「画像が置かれていない側」を含めていたため、
  片側運用では保存ボタンが有効にならなかった。**置いてある画像の必須入力だけ**を保存の条件とし、
  不在側は注記に留めるよう修正(受入条件4)。

## 7. 未解決事項

1. **画像の一括保存は未実装**。コピーリスト TSV で配置先を出すところまで(R3-FB から継続)。
2. **外した画像は元に戻せない**(append-only の一方向)。やり直しは置き直しで行う。
   R3-FA / R3-FB と同じ方針で、取り消しを入れると「最新が勝つ」判定が要り、時刻での優劣づけを持ち込むため。
3. **`crypto.subtle` が必要**。`file://` や非セキュアコンテキストでは読み込みを断る。
4. **パッケージは localStorage へ丸ごと保存**(実物 約382KB)。ケース数が増えると上限に近づく。
5. **タブは3つ固定**。`switchView` は3分岐のまま。
6. 比較の先端が複数ある(ambiguous)ケースは画面に注意文を出すだけで、解消UIは無い。
7. **`ChatGPTで生成` の model 名は固定文字列**(`ChatGPT Images UI`)。実際のモデル名を記録したい場合は
   「その他」か、後から「生成条件を変更」で入れ直す。
